# Участие в проекте

В этом документе описаны правила внесения изменений в репозиторий. Руководство будет постепенно расширяться по мере развития проекта: сюда можно добавить правила работы с ветками, Pull Request, проверки кода и автоматизацию.

## Сообщения коммитов

Для сообщений коммитов используйте соглашение [Conventional Commits](https://www.conventionalcommits.org/).

### Формат

```text
<type>(<scope>): <description>
```

- **type** — тип изменения.
- **scope** — область проекта, которой касается изменение. Указывайте её, если она помогает понять назначение коммита.
- **description** — краткое описание изменения.

Используйте строчные буквы в типе, области и описании. Не ставьте точку в конце заголовка коммита. Формулируйте описание кратко и по существу, например: `add`, `update`, `remove` или `correct`.

### Типы коммитов

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `feat` | Добавление новой возможности или нового поведения | `feat(airflow): add full refresh DAG` |
| `fix` | Исправление ошибки | `fix(spark): correct timestamp parsing` |
| `refactor` | Изменение структуры или кода без изменения внешнего поведения | `refactor(infrastructure): reorganize database directories` |
| `docs` | Изменения документации | `docs(architecture): describe Airflow integration` |
| `test` | Добавление или изменение тестов | `test(silver): add data quality checks` |
| `chore` | Обслуживание и прочие технические задачи, для которых нет более подходящего типа | `chore(repo): remove obsolete files` |
| `build` | Изменения сборки, Docker-образов или зависимостей сборки | `build(docker): update Spark image` |
| `ci` | Изменения конфигурации непрерывной интеграции и доставки | `ci(github): add validation workflow` |

Выбирайте тип, который лучше всего отражает основную цель коммита. Не используйте `chore` как универсальный тип, если подходит более конкретный.

### Области изменений (scope)

Используйте короткие и единообразные названия областей проекта. Рекомендуемые варианты:

- `infrastructure` — Docker Compose и общая инфраструктура.
- `airflow` — DAG и конфигурация Airflow.
- `spark` — Spark jobs и конфигурация Spark.
- `iceberg` — таблицы Iceberg, работа каталога и метаданные.
- `minio` — объектное хранилище и связанные инструменты.
- `sql` — SQL-запросы и скрипты.
- `tests` — тестовая инфраструктура и тесты.
- `docs` — документация проекта.

Этот список не является закрытым. При необходимости используйте более конкретную область, если это делает назначение коммита понятнее.

### Примеры

```text
feat(airflow): add full refresh DAG
fix(spark): correct decimal conversion
refactor(infrastructure): reorganize database directories
chore(deps): update Python dependencies
docs(architecture): describe Airflow integration
test(silver): add data quality checks
```

### Описание коммита и дополнительные сведения

Если одного заголовка недостаточно, добавьте подробное описание после пустой строки. Объясните **что** изменилось и **почему**, а не повторяйте заголовок другими словами.

```text
refactor(infrastructure): reorganize database directories

- Move Iceberg PostgreSQL initialization scripts.
- Update the Docker Compose bind-mount path.
- Keep the existing PostgreSQL volume unchanged.
```

При необходимости используйте дополнительные поля (footers) Conventional Commits. В частности, несовместимые изменения отмечайте в конце коммита строкой `BREAKING CHANGE: <описание>`. Для таких изменений также можно поставить восклицательный знак перед двоеточием, например: `feat(api)!: change response format`.

## Перед созданием коммита

Перед коммитом проверьте состояние рабочей копии и подготовленные к фиксации изменения:

```powershell
git status
git diff --check
git diff
git diff --cached
```

Убедитесь, что коммит содержит только файлы, относящиеся к текущей задаче. Не добавляйте в репозиторий:

- файлы `.env`, учётные данные, пароли, токены и приватные ключи;
- дампы и резервные копии баз данных, если их добавление отдельно не согласовано и не проверено;
- локальные данные, результаты генерации, кэш и временные файлы;
- изменения, не относящиеся к текущей задаче.

Если файл уже добавлен в индекс Git, проверяйте его командой `git diff --cached`: обычная команда `git diff` не показывает подготовленные к коммиту изменения.

## Развитие руководства

Это начальная версия руководства. Правила именования веток, оформления Pull Request, проверки изменений и автоматизированного контроля будут добавляться по мере внедрения соответствующих процессов в проекте.
