# ADR 0002: Размещение прикладного кода и запуск задач через Airflow

- Статус: принято
- Дата: 2026-11-24

## Контекст

На текущем этапе проект использует Apache Airflow как оркестратор и стандартные механизмы запуска задач. Отдельный промежуточный execution layer (например, Apache Livy) пока не внедряется.

## Принятое решение

1. Весь прикладной код проекта на текущем этапе хранится в `applications/airflow`.
2. DAG-и и вызываемый ими код Python, Spark и SQL размещаются в Airflow-части проекта. Каталог `applications/spark` пока не используется; Spark-приложения отдельно от Airflow не храним.
3. Для запуска задач применяем стандартные средства Airflow:
   - TaskFlow API и `PythonOperator` — для Python-задач;
   - `SparkSubmitOperator` — для Spark-приложений;
   - профильные SQL-операторы провайдеров — для SQL;
   - другие штатные операторы и сенсоры — по мере необходимости.
4. Livy и универсальный execution layer в текущую реализацию не входят.

## Техническое следствие для Spark

При `client` deploy mode драйвер Spark работает в среде, где выполняется `spark-submit`. Поэтому код Spark-приложения, хранящийся в Airflow-части репозитория, должен быть доступен этой среде во время запуска. Конкретный механизм доступа/доставки кода учитывается при настройке Spark-задач.

## Бэклог: единый execution layer

В дальнейшем рассмотреть промежуточный слой для подготовки, запуска и мониторинга разных типов приложений: Python, Spark, SQL и других вычислительных задач.

В исследование включить:
- единый API запуска и передачи параметров;
- доставку исходного кода и артефактов в среду исполнения;
- получение статусов, логов и результатов, отмену задач;
- интеграцию с Airflow через операторы и сенсоры;
- разграничение ответственности между Airflow и исполнительной инфраструктурой;
- оценку Apache Livy как одного из вариантов для Spark, не предполагая заранее, что он станет универсальным решением.

До отдельного архитектурного решения используем стандартные операторы Airflow.
